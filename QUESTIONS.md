- Guard hardening: `.agents/hooks/guard-bash.sh`'s mkfs pattern only matches bare `mkfs`, letting `mkfs.ext4`/`mkfs.xfs`/etc. through (TASKS.md item). Cannot fix from inside the loop: `.claude/settings.json` explicitly denies `Edit(./.agents/hooks/**)`, and that same settings file denies `Edit(./.claude/**)` on itself, so no agent in this repo can widen the deny list to make an exception either. Recommendation: a human applies the one-line pattern widening directly (`mkfs` -> `mkfs(\.[a-zA-Z0-9]+)?`, whole-word/command-position match) and adds the corresponding test to test/selbstschutz.test.js. This is deliberate protection of a security-critical hook working as designed, not a bug — flagging so it doesn't sit silently unfixed at the top of TASKS.md every round.
- Guard false positive: `.agents/hooks/guard-bash.sh` sets `SCHREIBEND_IMMER` once it sees a bare token like `install` anywhere on the command line, then checks *every* token on that line — including words inside a quoted `git commit -m "..."` message — against `protected-paths.sh`'s `MUSTER_SELBST` (which matches the literal standalone token `.gitattributes`). Result: a plain, safe `git commit -m "install .gitattributes merge helper"` gets blocked as if it were writing to a protected path, even though it writes to nothing. Confirmed by direct testing during round 4 (coder had to reword a commit message to avoid this; the actual commit 73c0c41 went through once reworded). Cannot fix from inside the loop for the same reason as the mkfs gap above: `.claude/settings.json` denies `Edit(./.agents/hooks/**)` to every agent. Recommendation: a human makes the guard commit-message-aware — e.g. skip the protected-path/dependency/test-file checks for tokens that are part of a `-m`/`--message` argument's string, rather than scanning the whole raw command line token-by-token. This is a usability gap (safe commands get blocked, forcing awkward message rewording), not a security hole, so it is lower priority than the mkfs gap.

- ECONNRESET fix (round 9, top TASKS.md item, grade 7.3 -> 6.8) is blocked by a frozen test, not by missing effort: lib/anfrage.js:28 koerperLesen() calls anfrage.destroy() synchronously before rejecting on an oversized body. Node's IncomingMessage.destroy() always destroys the underlying socket (there is no gentler variant), and request/response share that one socket in Node's http module, so any response written after destroy() is a no-op regardless of call order -- the only real fix is to never call destroy() on this path (guard further 'data' events with a boolean flag instead, and let the connection drain and close normally). But test/anfrage.test.js:145-155 ("koerperLesen bricht ab, sobald die Grenze ueberschritten ist") explicitly asserts destroy() IS called on the fake anfrage double, that file is git-tracked, and guard-files.sh blocks Edit/Write on any git-tracked file matching MUSTER_TESTS (confirmed by reading the hook script directly) -- same structural block already documented for the anfrage-wurzel duplication item above. Considered and rejected: deferring the destroy() call to a later microtask/macrotask so the test's post-await check still sees it as called -- this only works by accident of Node/V8's internal microtask ordering between assert.rejects' own await and a sibling Promise.resolve().then(), is not guaranteed by any spec, and reintroduces the exact same race against server.js's res.end() that causes the production bug in the first place, just with lower probability. Recommendation: a human drops or rewrites the destroy()-assertion line in that one test (the rest of it -- that koerperLesen rejects with "Zu gross" -- is correct and should stay), then the code fix (remove the destroy() call, add the boolean guard) is a five-minute change.
